# TableTheory v3.0.6

## Behavioral change carried forward from v3.0.5

TableTheory v3.0.5 changed ordinary Go `Create()` to always apply `attribute_not_exists` to the partition key. `Create()`
now returns `ErrConditionFailed` when an item with that key already exists instead of overwriting it. This fixes the
silent-overwrite bug reported in [#523](https://github.com/theory-cloud/TableTheory/issues/523) and aligns ordinary
creates with transactional creates ([#524](https://github.com/theory-cloud/TableTheory/pull/524)).

### Who needs to migrate

Audit Go `Create()` call sites that intentionally overwrite or upsert an existing item. Typical affected sites include
repeated writes to stable caller-chosen keys and `Set`, `Update`, `Upsert`, or `Store` paths implemented with `Create()`.
Change only those sites to `CreateOrUpdate()`:

```go
// Strict create: keep this when an existing item must make the write fail.
err := db.Model(&record).Create()

// Intentional overwrite/upsert: use this when the same key may already exist.
err := db.Model(&record).CreateOrUpdate()
```

Call sites that require strict create-only behavior need no changes. Do not broadly replace every `Create()` call;
keeping strict creates strict preserves duplicate-write detection and the correctness fix from #523.

### Runtime symptom

An affected write returns a condition-check failure, which callers can detect with
`errors.Is(err, theorydbErrors.ErrConditionFailed)`. Callers that log, downgrade, or swallow that error can appear to
succeed while the stored item stops changing.

### Test condition-sensitive behavior

The simple doubles in `pkg/mocks` replay configured calls and returns; they do not build or evaluate DynamoDB condition
expressions. Duplicate-create condition failures therefore cannot surface naturally in those mock-based unit tests. Use
the state-backed `pkg/testing/fakedb` fake for condition-sensitive tests: it stores items and evaluates the supported
condition expressions, including the `Create()` partition-key not-exists guard. Use DynamoDB Local for behavior outside
the fake's scenario-validated scope.

For the complete audit and migration procedure, see the
[v3.0.5 `Create()` migration guide](https://github.com/theory-cloud/TableTheory/blob/main/docs/migration/v3.0.5-create.md).
